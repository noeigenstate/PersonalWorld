## 场景变化

### 同一条流程应用到所有地点

旧流程只在矢量瓦片中发现具名公园/商场 POI 后，才查询 OSM 细节。因此普通街区、居住区域和一些郊游地点会一直停在较粗的建筑和绿地层。

现在所有按照片精确位置请求的区域都可以补充有界、缓存的 OSM 细节：建筑足迹、已有高度/楼层、用途、绿地、水域、运动场和地点 AOI。补充不可用时保留基础瓦片。服务端仍只向公共地理服务传坐标范围，不发送私人照片与卡片。

详细建筑与瓦片楼体按实际交叠面积去重，保留大裙房，继承已有楼高；详细绿地做多边形合并。商业用途的大低层楼新增玻璃窗带、浅色柱肋、奶油层带与屋檐；真实凹形轮廓和院落孔洞保留。普通住宅和高楼仍使用已有统一立面。

缓存同步升级：后端 `v6`，前端 `v6:`，细节来源 `details-v4`。避免旧缺少普通建筑的缓存一直有效。

这不是每个地点都新建一座专属地标。拱墅两馆、城北万象城/塔楼、环球中心、滘尾角灯塔仍使用原有精修资产；未核实的建筑不伪造专属外形。

### 全相册覆盖检查

本机配置 `MEMORY_REVIEW_LOCAL=1` 后，`useSceneCoverage.ts` 对当前账户的真实街道级照片分组，顺序调用与地图相同的场景接口；界面显示准备进度。元数据快照保存在账号哈希对应的 `server/data/memory-review/` 文件里。

- 仅含照片 ID、日期来源、定位、信息卡与场景数量/状态。
- 不包含原片、预览、文件名、文件哈希、登录凭据。
- API 要求登录、隐私声明、写入来源标记；快照按账户隔离，不接受任意文件路径。
- 默认未设置本机开关时不导出。目录在 `.gitignore` 中。
- 精度仅为城市/区县、缺少坐标的照片不伪造街区。

首次交付时未能连接用户浏览器，真实覆盖和 MP4 均未完成。用户随后打开页面，2026-09-27 已收到真实快照并完成后续检查。此前的等待状态已解除。

`tests/scene-coverage.mjs` 接收 `MEMORY_REVIEW_PATH`，对快照里的每一个区域在真实高德地图上截图；照片用匿名色块代替。前后结果分别保存在忽略目录 `data/exports/scene-coverage/`、`scene-coverage-after/`，含每区的原始建筑数、实际生成数、缩放、地标和截图。16 处均成功装载，但**加载成功不表示建筑完整，更不表示专属精修通过**。目前只用少于 50 栋/细节来源失败标记保守待补，不把它解释成地理覆盖百分比；密集场景也可能缺一整片小区。

本次实测：天目未来谷 0 栋；若干沿海区域 3–4 栋；另有杭州、南京居住/商业地点只有 38–48 栋。现有精修资产仍限于拱墅两馆、城北万象城两栋、环球中心、滘尾角灯塔。9 张未进入精确地点分组的照片没有可用定位，不伪造位置。新界面显示“街区资料 / 待补”，不再显示容易误导的“已准备全部街区”。

还修正了整片地面覆盖：旧逻辑只要全区建筑数达到 100 就铺不透明底板和整片用途地面，可能盖住同区缺少 OSM 足迹的原生建筑。现在取消这些覆盖层，保留所有实际生成的建筑、地标、湖河、道路、草坪、树和透明投影面。街区底图用轻微暖色滤镜统一色调，不生成假地面填空；`sceneSurfaces` 改为 `mapped-only`。再次检查全部 16 处，各处建筑数量未下降；公园近景确认两馆和湖河仍在。

额外按 [Overture 官方建筑说明](https://docs.overturemaps.org/guides/buildings/) 和 [官方有界下载客户端](https://docs.overturemaps.org/getting-data/overturemaps-py/) 试查了未来谷及一处杭州缺口，指定发布版的查询返回无数据，尚不能用于补齐。未下载整国数据或替换现有来源。真正补齐仍需有可用的建筑/地形资料，并为特殊建筑制作有依据的资产。

### 美术变化与局限

- 树冠从低细分硬面改为同一平滑圆润几何，保留尺度变化；主要树色由四种收敛到两种。少量漫反射补色避免阴面过灰。
- 半球光从默认 Y-up 修正为地图实际 Z-up，提高柔和环境光。不会改变地理坐标和相机。
- 水面按观察角度增加反射权重，叠加缓慢宽高光；没有引入新模型服务或新渲染引擎。
- 仍是平面水面，未加入立体破浪、海底折射、全场景环境遮蔽。高德原生楼体与 Three.js 分属画布，深度和反射依然不共享。
- 保留已有街区模型和水系；无论总建筑数量多少，都不铺覆盖未重建楼块的大面积底板。数据缺失的楼体仍需补来源，不能称为已卡通化。

## 短片：从地点数量排序到活动篇章

此前只选照片最多的前四个地点。现在新增至少三张、有明确画面活动的雪地/甜筒/手工候选，同时保留至少两张的具体地点候选（最多 24 处）。每批自动尝试最多三条，剩余可在短片界面的候选列表选择，仍无需创意输入。稳定来源 key 与尝试记录避免相同素材因批次变化重复生成；暂停仍有效。

候选发现读取全部可用信息卡，选定主题后才均匀限制到最多 80 张送给导演，避免相册一大就先把小地点的几张照片全局采样掉。尝试记录保留最近 256 项，并非无限历史。旧版自动修复仅匹配 1–3 版任务，避免新版本降级后反复创建修复任务。

导演现在输出镜头作用 `beat` 与运动 `motion`，每张 3.2–5.5 秒。同日没有精确时间时保留导演的环境/动作/细节排序，跨日保持可靠日期顺序。原来按 UUID 排同一天照片，会破坏镜头安排，现已修正。

渲染器有四种内容驱动方向，不随机套皮；不同留白、图框尺寸、颜色、转场速度和原创合成配乐节奏。静止、推进、拉远、轻漂移均限制在保留整图的范围。尾镜头同时显示动作字幕和结语，预留排版空间。

真实编排中发现“第一支冰淇淋”缺少事实依据，已补入校验；没有依据的上午/下午、亲子称谓、首次与成长断言不能直接出现在字幕或编排说明。现有自然语言规则仍不完整，不宣称零幻觉。

三支真实影片均通过 ffprobe 音视频流检查及 FFmpeg 全长解码，并实际查看中段照片/字幕布局。它们有不同的色彩、节奏和配乐，但结构仍是同一家族的照片相册，不能声称已具备成熟的个性化成长叙事。雪地片中“醒啦”把两张不同状态的照片衔接成了先后故事，说明仅靠现有单图描述和日期还会产生叙事推断；未来需保留精确拍摄时间、明确连续动作证据，并接入人物库。

自动导出已接通：本机 `.env` 设置 `MEMORY_FILM_EXPORT_DIR=./data/exports/films`。`server/memoryFilmExport.mjs` 在渲染成功后把 MP4、海报、精简交付清单写入账户隔离目录；先临时文件写入再重命名。服务重启会补导已完成任务；导出失败保留可播放成片并在清理时重试，未导出前不因 24 小时/8 条预览上限删除它。自动导出的副本不受预览缓存期限影响；不自动弹浏览器下载窗口，不公开文件系统路径，不把任何成片提交 Git。本机当前 8 支缓存成片均已补导。
