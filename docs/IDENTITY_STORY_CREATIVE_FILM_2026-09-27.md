## 用户目标与本轮边界

用户要求先提交、推送上一轮成果；确认地图 skill 能否对任意地点自动生成同品质专属模型；若能，则完成现有 16 区。另要求新地点自动提示、提升影片创意，并真正接通“单图理解 → 人物一致性 → 人生故事 → 自动 MP4”。

上一轮已提交并推送：`5cc8052 feat: audit regional scenes and export themed memory films`。

**地图目前无法保证任意地点自动达到拱墅体育场馆的专属精修品质。** skill 已固化参考分析、轮廓、结构、立面、材质与验收的制作流程；运行时已有通用场景与已注册资产的自动加载。尚缺通用的地标资料获取、专属资产生成、质量评估和返修闭环。真实足迹和多角度参考也并非处处具备。当前 16 区中，上一轮检查有 7 区建筑资料稀少，其中 1 区没有取得建筑轮廓。

本轮没有冒称完成 16 处专属模型，也没有删除已有精修资产或重铺不透明地面。本轮地图工作是把真实覆盖与新地点提醒做成正常产品功能。其他开发集中在人物、故事和影片链路。

## 页面中的入口

- 顶部 **人物与故事**：候选人物、确认称呼、逐张纠错、故事章节及其照片依据。
- 地图左上 **照片区域**：全部区域的通用场景、附近专属模型、资料不足和加载状态；新地点带标记。
- 顶部 **回忆短片**：自动出片、播放、下载、暂停、可选章节。无需创意提示词。
- 单图信息卡增加 **人物库关联**；使用用户已确认的称呼，当前照片的匹配可以纠正，原有视觉描述仍保留。
- 人生管家可以读取服务端人物及故事依据；不能将候选分组、派生章节标题视为用户确认的事实。

## 一、正常导入到新地点通知

`useSceneCoverage.ts` 使用与地图相同的 `photoRegions` / `fetchRegionScene`。准备全部有精确位置的区域，按 `landmarkCatalog.ts` 与渲染器共用的建筑 ID 注册判断附近专属资产。

区域状态会写入账户 IndexedDB 的 `scene-coverage`。新增照片如果属于原区域，以照片成员交集延续通知身份；新区域标记为新地点。打开清单后标为已读，刷新仍保留。失败有具体原因，少于 50 栋的提示只是来源稀少的保守规则，不是完整度百分比。

`MEMORY_REVIEW_LOCAL` 现在只控制可选的本机元数据检查快照，不再是自动准备街区的前提。照片位置信息不足时不能伪造区域。当前存在专属模型的区域也仅标“附近含专属模型”，不等于区域内所有建筑完成精修。

本轮实际账户复核：62 张照片、16 个区域，16 区均完成资料加载，7 区触发资料稀少提示。`ready` 仍只表示加载成功。

## 二、三层记忆及增量处理

```mermaid
flowchart LR
  A[账户内照片与 EXIF] --> B[StepFun 单图信息卡]
  A --> C[本机人脸检测与特征]
  C --> D[候选人物与人工确认]
  B --> E[有来源的事实和事件]
  D --> E
  E --> F[故事章节与依赖版本]
  F --> G[自动导演选片]
  G --> H[原片上传到本机剪辑器]
  H --> I[MP4 与持久导出]
  E --> J[照片信息卡与人生管家]
```

### 1. 单图理解

沿用现有 StepFun 信息卡自动队列，空闲时处理真实照片，两张并发；已有卡片复用。EXIF、地理元数据、视觉观察和用户确认保留不同来源。卡片里的“像是母亲”“睡着”等仍可能识别错误，不能据此生成稳定姓名或亲属身份。

### 2. 人物一致性

参考用户提供的 face-detection-embedding-identity handoff，采用“检测、归一化特征、持久观测、增量运行、人工纠错”的结构。本机实现采用 **OpenCV YuNet + SFace**，没有宣称安装或运行 InsightFace。

- `identity/worker.py`：CPU 检测、对齐、128 维特征、清晰度分档、128px 人脸缩略图。中文路径先读字节再 `imdecode`。
- `faceEngine.mjs`：串行 worker、单请求超时、空闲退出。模型指纹包含两个模型文件及 OpenCV 版本。
- `identityStore.mjs`：Node 内置 SQLite，账户单独目录，WAL；记录 assets / runs / people / faces / corrections / manual_facts。
- 同一内容 hash 与模型版本的照片不重复提取；卡片文字更新只更新事实。新增照片增量匹配；失败可重试。
- 同图两个人脸禁止自动并为同一人。高质量增量匹配检查原型、中心、锚点和候选差距；低质量匹配只保留候选状态。
- 未确认的候选在批次结束做有约束聚合：组间平均相似度至少 .60、最小跨组相似度至少 .42、同图互斥、同模型指纹。它用于方便人工核对，不自动变成确认身份。不能用简单相似边连通分量无限合并。
- 人物 UUID、用户名字/关系和人脸观测分开。命名确认、移入、拆组、整组合并、忽略、撤销都能执行；人工调整的观测会锁定。合并保留目标 ID，迁移来源事实；撤销仅在后续状态尚未变化时可用。
- 删除照片同步清理对应特征观测、运行记录、缩略图和失去所有来源的照片范围补充。原片上传本机分析后删除临时 JPEG。

**真实运行数据**：62 张照片全部完成本机检测，58 张检出合计 83 条人脸观测，4 张无可用人脸；当前 37 个候选组，最大两组分别 20、17 条观测。已确认人物为 0。候选组数不代表实际人数，也没有给真实照片擅自起名。

这些阈值是初始工程配置，尚无该相册的人工身份真值，不能报告准确率。侧脸、遮挡、小脸、儿童年龄变化仍会拆组。候选批次聚合最多处理 400 条未锁定观测；更大相册走增量原型匹配，尚未进行万人/百万照片规模压测。已确认身份的模型升级保留人工信息并要求单独迁移，不跨模型混比。

### 3. 人生故事

`storyGraph.mjs` 按可靠日期、同一地点/时间段、活动词和已确认人物派生事件与章节，类型含同次片段、活动合集、同地重访与人物跨日时光。每条事实有类型、来源、照片/人物关联；每章有 factIds、eventIds、assetIds 和 revision。

真实相册当前形成 **23 个候选章节**。没有已确认人物时，这些是地点/活动/时间章节，不能称为已确认女儿的成长轨迹。人物库核对之后，相同稳定身份才进入跨日人物章节。

用户确认与可靠人物匹配优先于信息卡的视觉猜测。身份相同仍不能自动推出年龄、喜好或“第一次”。图谱是确定性派生，事实和人物变更会使相关章节指纹改变；昂贵的人脸提取按内容缓存，不因文字改名重跑。

## 三、真正改变影片的编辑方式

导演版本 `memory-film-6`，渲染版本 `creative-scenes-4`。

| 题材 | 画面与编辑 | 配乐 |
| --- | --- | --- |
| 雪地纪实 | 深青色章节、主体大画面、留白字幕、上一格回看、轻雪粒、慢淡入 | 疏朗钢琴音色与延音铺底，留出休止 |
| 甜筒拼贴 | 大编号、粉色/奶油/浅绿几何、大小照片并置、圆角主画面、较快擦入 | 较快的敲击音色、低音和轻节拍 |
| 手工创作簿 | 格纸、笔触装饰、主画面与书页留白、跨月章节、照片收藏页 | 带轻微摇摆节奏的拨弦音色 |
| 其他日常 | 生活相册、章节和照片收藏 | 柔和拨弦变体 |

配乐是本机合成的原创音符编排，不是下载音乐、克隆声音或模型生成的整首音乐。尚未增加旁白、真人视频理解或外部生成式视频服务。

StepFun 只接收选片所需的观察、时间和确认事实，不接收人脸向量，也不需要原片参与这一步。导演选择主题、字幕、时长、beat、layout、motion；程序校验真实照片 ID、强事实与时间顺序。当天 EXIF 时间完整时严格按时间排序，缺少时间不编造先后因果。闭眼不直接推断刚睡醒或玩累。

`creativeFilm.py` 通过 Pillow 合成真实照片、图形、文字与主题动作，以 RGB 帧流直接送 FFmpeg；不落盘大量私人逐帧图片。人脸框仅供本机裁切保护；没有可靠框或裁切会碰到人脸时展示完整照片，背景使用原片模糊色域。人脸像素不生成或替换。

每片包含独立开场、不同构图的主镜头、必要的跨月页和收尾。主题不是只换背景色；同时改变构图、节奏、装饰、转场和音乐。创意仍来自四种可编排的视觉语法，不是任意风格生成器，后续可继续扩充。

新环境配置：

```text
npm install
python -m pip install -r server/requirements-local.txt
python server/identity/setup_models.py
npm run dev
```

FFmpeg/FFprobe 单独安装并放入 PATH；中文字体优先用本机微软雅黑，也可设置 `MEMORY_FILM_FONT`。Python 路径可用 `FACE_PYTHON` 和 `MEMORY_FILM_PYTHON` 配置；模型目录默认 `server/data/identity-models`，下载脚本从 OpenCV 官方仓库获取模型、校验 SHA-256 并保存许可证。环境变量示例见 `.env.example`，实际 Key 不提交。
