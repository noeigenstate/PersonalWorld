# 持续理解、创意短片与参赛收敛

日期：2026-09-28。上一个完成并推送的基线为 `2e847f6`。

## 目标与本轮范围

人物名字、关系、照片描述变更后，系统应该重新理解相关经历，形成新的故事角度，再更新表达。用户无需重新填写短片创意，也不应该为同一份人物关系反复补充说明。

9 月 30 日下午提交作品。比赛 demo 小于 5 分钟、视频格式不限；征文记录参赛过程，格式与篇幅不限。本轮实现这条主链并准备演示材料。地图保留已经验收的真实地理场景和专属模型，不在交付前迁移地图引擎。

## 已实现的运行链条

```mermaid
flowchart LR
  A[照片观察 / 用户修改 / 身份确认] --> B[按内容计算相关事件版本]
  B --> C[持久队列重新理解事件]
  C --> D[跨地点发现故事角度]
  D --> E[独立证据复核与程序校验]
  E --> F[故事章节 / 人生管家上下文]
  E --> G[导演选片和镜头编排]
  G --> H[浏览器提供原片]
  H --> I[本机 MP4 / 自动导出]
```

### 持久队列

- 每个账户独立保存 `understanding.json`。原始照片观察、人物确认和关系继续保存在既有 SQLite 中；生成的解释单独存储，不回写为确认事实。
- 至少两张有观察的照片组成的事件进入语义重理解；单张事件仍进入跨事件故事发现。每个事件最多均匀采样 28 张，本轮不等同于无限相册规模的方案。
- 事件输入包含每张照片的观察、日期及来源、地点、人物 ID、适用的用户补充和关系。内容、skill 文本、模型 ID 参与任务版本。
- 连续资料修改合并约 8 秒，每账户一次执行一项任务。未变事件复用结果；变更期间返回的旧结果不作为当前解释发布。
- 服务启动扫描已有账户并恢复队列。文字资料已在服务端，浏览器关闭时仍可继续；需要原图的检测与短片上传仍依赖登录相册。
- 推送时合入远端 `b750490`、`1e113e4`、`b26e775`、`d3b305d`：地点内人生管家、账户硬盘备份、液态玻璃界面、重复照片整理。备份成功后原图也在账户 vault 中，浏览器 IndexedDB 变为缓存；本轮影片/检测调度尚沿用浏览器供图，没有宣称已接入关闭浏览器后的全自动成片。新版备份隐私声明由用户在页面确认。
- 失败保留原因，不对同版本无限重试；页面可显式重试。模型结构修复最多一次。暂停停止新请求，已在服务端进行的请求返回后不发布为当前结果。
- 记录最近 40 次源版本变化，页面显示最近 6 次的状态资料；这不是全历史事务日志。

### 两级理解与复核

1. `event`：理解一次经历，保存标题、摘要、带照片依据的线索、物品/活动和必要的资料缺口。
2. `library`：从整批事件与原始观察发现关系、物品、重访、细节或出游主题。通常提出 3–5 个，素材不足时允许更少。
3. 独立证据复核：第二次模型调用同时获得原始逐图成员资料与候选，纠正把局部未知人物套为已知亲属、从不在画面推断没有同行、从食物推断固定偏好等错误。
4. 程序核验：照片 ID 必须存在；每段证据和编排步骤绑定照片；已知但不在所选照片中的人名不能迁入；部分强个人断言必须有用户依据；高度重叠的同类候选合并。

复核中也发现过模型改写“同日”和活动先后的错误。最终用于展示和传给导演的照片证据、步骤内容直接取原始观察与日期；保留模型选择的照片组合、角度与通用镜头方向。日期可靠性仍取决于原资料，不能把文件名估计当成精确 EXIF。跨类型候选优先排列，避免自动名额连续消耗在同一类表达上。

首轮真实运行确实出现“未匹配的海边老人被写成姥姥”、以及“没有其他家人”的无依据解释。这促成本轮独立复核、逐步骤证据与排除性断言约束。模型复核和字符串规则无法证明所有自然语言事实正确，输出继续标为故事理解，用户确认始终有更高优先级。

已知检测边界保留：被讨论的 2 月 19 日海边照片仍未检测到第二位人物。不能声称这一身份漏检已经解决，也没有手动将她指定为姥姥。关系库中已确认的资料不会丢失；有可靠人物关联的其他照片可以使用它。

### 创意进入真实成片

- 新故事章节包含稳定 key、所选照片、人物、角度、带照片 ID 的具体步骤、通用镜头方向和证据。
- 导演输入当前照片事实与 `creativeBrief`，不直接把上一段创意当作事实。事实与角度都参与缓存；同一组照片可以形成有不同表达意义的作品。
- 自动队列优先修订事实变化的影片，然后修订章节，接着每轮理解最多自动尝试两支新创意短片。其余候选可一键生成。暂停和既有防重复逻辑保留。
- “陪伴双页”：奶油与鼠尾草色、错落双页、连线和大画面回看、呼应式轻钢琴编排。
- “细节短诗”：深绿背景、较大单幅、字幕延后出现、安静转场、疏朗钢琴和低声部。
- 保留甜筒拼贴、雪地手记、创作簿和生活相册。具体待遇由实际选片内容及已验证的故事类型选择；不让模型任意指定脚本或执行命令。
- 原图主体和人脸不生成、不改写；有可靠人脸框且裁切安全才允许局部填充，否则保留全片。配乐为本机原创合成，当前没有配音。
- 页面在后台时，持续理解有任务也继续检查状态，避免用户保持页面打开却迟迟无法进入成片。浏览器自身仍可能节流后台定时器。
- 现有作品仍保留 24 小时/最近 8 项预览，已导出 MP4 独立保存。所有历史作品的长期依赖登记尚未实现。

## 任意地点同品质：直接回答

之前体育场馆的精修模型由开发 agent 根据参考资料编写 Three.js 程序化几何。skill 固化了资料获取、辨识特征拆解、美术约束、制作和验收流程；运行时能够调用已登记资产与通用场景，尚没有一个可保证任意地标同品质的无人值守资产工厂。

工程上可以继续提高自动覆盖率：地点实体合并 → 资料包 → 类别模板/专属资产 → 多视角地理与美术检查 → 有界修复 → 缓存发布。缺乏地理数据或参考图、独特曲面造型、遮挡、远近景性能都会影响成功率；不能在未测大量地点时承诺百分比。比赛前优先保持当前可辨识地点、场地合并和稳定展示；把自动精修验收服务放在后续，不用两天重建整个资产生产栈。
