## 2. 产品背景与用户真正要的结果

项目名 Personal World／人生地图。用户导入自己的照片，程序读 EXIF、文件名、GPS 等，整理成事件，在地图和时间线上浏览；StepFun 生成照片信息卡、辅助定位、分析事件并为人生管家提供回答。地图场景的价值应服务于**照片对应的个人记忆地点**，而非单独做一个普通 3D 城市地图。

地图部分经过多轮讨论形成的需求：

1. 保持真实地理结构、真实照片定位、地图自由拖动和缩放。概念图 [`mockups/map-style-direction-2026-09-25.png`](mockups/map-style-direction-2026-09-25.png) 是视觉目标，不能用一张静态图代替交互地图，也不能把建筑随意移走。
2. 不只做东方明珠样板。用户已导入很多私人照片，要按**有照片的区域**生成，并因地制宜；没有代表性地标的地点也应有统一、丰满的卡通视觉。最初设想华东优先，随后用户明确要求覆盖当前有照片的各个区域。
3. 视觉目标包括丰满的楼体、统一的建筑语汇、树木、草坪、路面、水面质感与反射、真实方向的光照和阴影、整体暖色调。相似元素可以复用少数造型并调整大小。概念图的丰富度和统一性是评价重点，用户尤其不接受白膜、随意画圆、巨大平面覆盖街区、把真实高楼换成矮小假楼。
4. 照片信息卡应为局部场景提供主题证据，例如海滩、冰淇淋、课堂、演唱会、开车、阅读等。一组照片表达的事件主题应能影响建筑表面或合适的场景装饰，但不应凭主题捏造地理事实。
5. 全图和较小缩放级别也要有相近的视觉语言，且须考虑地图可读性、性能和真实性；近景精细场景不能简单等同于“全缩放卡通化”。
6. 地图上一组内的每张照片应能打开；真实私有照片应是处理对象。用户还希望自动生成信息卡，了解故事线现状。

参考的 UE 项目是 `F:\future\digital_new_rome`，用户曾要求先从其 Git 记录找线索再看文档；本网页场景目前未直接复用 UE 的地球引擎或资产。不要把参考项目误当作现有 Web 地图渲染后端。

## 5. 为什么用户看到“素材没了”：已知事实与待证假设

**确定的代码事实：**

- 普通照片的旧通用圆形小景已删；普通区域若没有可见的 `regionalMemory` 输出，视觉就会回到高德底图。这是对前一版错误覆盖的过度纠偏。
- `focusMemoryScene` 先清空旧 Three.js 组，再异步取区域数据；失败分支目前只重新 `draw()`，不显示明确错误。用户容易只看到空白或原生地图，无法知道是瓦片失败还是没有可渲染元素。
- `AMap.Buildings.setStyle` 会在切换／清理局部替换区域时改变原生建筑；独立 WebGL 画布的深度与高德不一致。此前有过“原生楼整片暂时消失”的浏览器观察，已撤销广域染色，仍需实地验证剩余局部 `setStyle`。
- 建筑选择器有严格面积、距离、高度限制；它能防止损坏高楼，也会让数据稀疏的区域没有卡通楼。一次对与用户问题相似的稀疏区域数据检查只得到极少建筑足迹、没有绿地，自定义建筑候选为零，主要只剩路旁树。这里不记录私人坐标。
- 近景触发依赖精确定位、zoom、相机距离和开关；地图标记能显示，并不保证场景触发。仅有省／市级推断位置的照片不应被当成有可靠街区坐标。

**尚未证明的原因：**用户这一次白膜画面究竟由哪一个条件造成。我们没有进入用户同一浏览器的私有账户；自动化 Chrome 使用独立配置文件和模拟照片／卡片。也可能存在旧页面未重载、照片精度与预期不同、真实 `/api/map-scene` 返回错误、目标区域 OSM 缺数据、实际相机不在 450m 范围内、图层时序或视觉密度问题。需要先取证，不能提前选一个原因宣布“修复”。

## 7. 本机启动与检查入口

项目根目录运行 `npm run dev`，浏览器打开 `http://localhost:5183/`；本机 API 默认在 `127.0.0.1:8787`，Vite 代理 API。若依赖尚未安装，先运行 `npm ci`。局域网命令 `npm run dev:lan` 使用 HTTPS；用户若原先在 HTTP localhost 导入照片，改用 HTTPS、IP 地址、其他端口或另一浏览器后会看到不同的 IndexedDB，不能把“照片不见”误诊成代码清空数据。先确认用户原本使用的完整网址。

编译检查为 `npm run build`；实际高德地图合成流程是 `npm run test:amap`；公开武汉场景预览是 `node tests/scene-region-preview.mjs`，其截图默认写入系统临时目录，命令需要 `.env` 中的高德配置和运行中的开发服务。不要把预览脚本的 `SCENE_LNG`／`SCENE_LAT` 指向私人家庭地点并上传输出。若直接从终端请求 `/api/map-scene` 得到 401，先检查登录 cookie 与 `x-memory-agent: web`，这并不能证明浏览器中的场景接口坏了。

## 8. 给下一位 agent 的复现与验收顺序

1. **保全现场。** 记录 `git status --short --branch`、当前 HEAD、未提交 diff 和未跟踪文件；记录用户正在用的页面完整 origin、账户（无需密码）、3D 开关、浏览器、缩放级别和目标照片的定位精度。不要复制私人照片、照片文本、凭据或精确家庭坐标进公开测试、提交或聊天报告。
2. **同屏取证。** 让用户当前页面停在确实显示白膜的照片区域，取得该页截图和浏览器控制台／网络的最少必要信息：`/api/map-scene` 是否发出、HTTP 状态、返回各类要素数量；DOM 中 `.map-scene-source`、`.map-scene-caption` 是否可见；3D 开关与实际 zoom。需要与用户现有浏览器协作时，先确认该浏览器可被工具连接；此前工具枚举不到任何已连接浏览器，所以先前无法查看其私有页面。
3. **按触发链定位。** 顺序检查 `mapPhotos` 是否有坐标，`hasStreetLocation` 是否成立，zoom≥16.7 且距区域中心≤450m，`focusMemoryScene` 是否执行，异步请求是否被清空／过期，地理数据实际有多少合格足迹，`landscape.group`／`ordinary.group`／`memory.group` 的子对象数，`sceneAreas` 是否误隐藏原生楼。这里优先写可重复的诊断输出或受控断言，再动美术逻辑。
4. **固定相机对照。** 先拍当前真实画面，再用同位置、同镜头、同窗口比较每次修改。至少选三个真实数据条件：有水和大量楼的密集区、普通低楼／公园区、OSM 建筑数据稀疏区；再测有主题与无主题卡片、后台连续生成其他区域信息卡、缩小再放大、关闭／打开 3D。仅在用户同意时用其私有照片现场验收，不把原片放入仓库。
5. **设立可见的退化处理。** 区域请求失败、要素为空、无合格替换楼等应在界面和诊断中能区分；原有高德楼不可因卡通场景失败而消失。不要恢复巨大通用圆盘或整块不透明 OSM 地面，因为用户已明确否定过。主题装饰需有照片证据且符合地理落点。
6. **再做产品判断。** 通用地图与概念图的最大差距是全域底图／地面材质、建筑形体与视觉密度，不会靠补几棵树或颜色罩消失。若比赛时间有限，应明确与用户确认重点展示区域及视觉验收样本；自由浏览和真实地理结构是用户已确认的硬约束。需要完整全缩放视觉语言，可能要发布高德自定义样式，或引入可完全控制的矢量底图／3D 渲染管线；这不是当前代码已完成的能力。

**完成定义：** 用户自己的照片地点，在同一浏览器经硬刷新、切换区域及重访后稳定出现与照片主题相符且地理结构正确的卡通场景；每组照片均可点开；无巨面遮挡、无误删高楼、无显著白膜回退；公开样本和真实私有样本都通过同镜头截图对照，并由用户实际看到、认可。`npm run build` 或合成 Playwright 通过只能作为附加证据。
