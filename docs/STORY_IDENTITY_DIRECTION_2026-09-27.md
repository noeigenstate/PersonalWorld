# 从照片信息卡到可信的人生故事

日期：2026-09-27。回应用户对单图理解、自动故事图谱、增量人物一致性和短片创意的要求。本文区分现有能力、本轮改进和下一步方案；没有把设计方案写成已经运行的人脸识别系统。

## 1. 当前判断

项目已经可以把真实照片放回真实地点，自动得到信息卡，并自动剪出可播放的回忆。核心价值接下来在于：**同一个人、同一件事和同一个地方，经过长期积累后仍能被正确记住，并自动组织成值得回看的故事。**

地图是很好的回忆入口和参赛展示画面；继续统一场景质量有价值。下一阶段最高优先级应是人物身份与事实来源，否则扩大照片量后，地图更丰富，故事却可能把人认错、把推测当事实。

## 2. 单图理解：实际表现与证据范围

本轮审阅了上一轮保存的 **62 条真实照片信息卡摘要**、单图/跨图运行时代码、既有真实评测和已确认的人物纠错。摘要存在本机忽略目录，没有复制进公开文档。摘要审阅不能替代逐张原片的人工标注，因此不报告整本相册准确率。

| 能力 | 当前看到的表现 | 使用方式 |
|---|---|---|
| 场景与物品 | 能描述雪地、雪上游乐设施、沙滩、甜筒、羽毛球、白板、画笔和商业空间；细节丰富 | 足以发现活动主题、选择回忆候选 |
| 动作与互动 | 抱着休息、拿甜筒、制作砂画、白板绘画等较具体 | 用于镜头字幕；不能从单帧推断完整行动过程 |
| 元数据 | GPS、EXIF、文件时间来源在程序侧区分，地点优先使用更可靠来源 | 作为地点和时间索引；保留来源等级 |
| OCR / 地点推断 | 地标和清晰文字有用，小字、反光和车牌存在误读 | 继续保守校验，不让车牌单独把照片定位到某城市 |
| 人物身份 | 同一相册的孩子被写成男孩/女孩；已由用户确认的海边人物也曾被误写年龄和称谓 | 不能直接成为持久人物标签 |
| 事实与猜测分开 | 已有 skill 要求区分，但部分 `scene` 仍混入“家长”“亲子活动中心”等判断 | 下游必须把模型描述当观察候选，而非用户确认 |
| 成长里程碑 | 没有可靠的跨图身份、生日/年龄锚点和首次发生证据 | 暂时不能自动声称第一次、长高、越来越熟练或偏好改变 |

历史评测：2026-09-24 的 `photo-card` 同一图重复五次，规则项为 44/45；`photo-context` 四类场景各三次，规则项 48/48。它们证明这些小样本中 skill 对来源与保守判断有帮助，**不是 97.8% / 100% 的全相册语义准确率**。原记录位于 `skills/photo-card/evals/2026-09-24/` 和 `skills/photo-context/evals/2026-09-24/`。

### 现有计算流程

1. 原片在当前账户 IndexedDB；自动队列并行两张，已有卡片复用，可暂停。
2. 原片经 HEIC 兼容处理，最长边 2560 px JPEG，失败回退预览。
3. 服务端把图像与必要元数据、`photo-card` skill 发给 StepFun。
4. 服务端校验字段与部分地点规则；浏览器保存卡片。需要时由高德补充地点。
5. 事件分析仍有主动入口，单图完成不代表事件已确认。跨图线索也是候选，不等同于完整自动图谱。
6. 短片导演现在主要读取卡片文字，**没有再次逐图视觉审片**。所以当前剪辑容易继承卡片中的误判，也不知道具体人物在画面里的位置。

本轮补强了人物中性称呼、禁止凭单图外观判断家庭关系与跨图同一身份的 skill 规则。它对后续生成生效；没有静默改写已有卡片，也没有重新分析整个相册。短片增加无来源时段用语校验，消除仅凭日期写“下午”的一类问题。自然语言校验仍不能证明全部句子正确。

## 3. 人物一致性：目前确实缺少

代码核对结果：`MemoryEvent.people` 是文字数组，`PhotoCard` 是叙述和线索；短片补充仅按账户、照片 ID 保存。当前没有人脸框、embedding、稳定 person ID、自动身份候选、合并/拆分审阅，也没有人物增量索引。

用户提供的人脸识别交接文档（旧项目的人脸模块说明） 非常适合成为迁移依据。应提取其中的人脸模块，不整套搬运其素材管理、其他模型和工具集成。

### 推荐连接方式

```mermaid
flowchart LR
  A[当前账户的照片] --> B[本地检测与 embedding]
  B --> C[匿名人物候选]
  C --> D[命名、确认、合并、拆分]
  D --> E[稳定 person ID]
  A --> F[单图观察与可靠时间地点]
  E --> G[人物参与的事件]
  F --> G
  G --> H[出游、重访、活动、成长篇章]
  H --> I[地图入口与自动短片]
```

“相似人脸”回答可能是同一个人；“这是我女儿”属于用户确认的人物关系。两个信息应分别保存。对用户最少的操作可以是首次审阅时确认本人和女儿、纠正几个不确定候选；不要求用户为每支短片写创意。

### 建议保留的数据

| 对象 | 关键字段与作用 |
|---|---|
| Asset | 稳定 asset ID、内容哈希、是否可访问；删除和重新导入有明确语义 |
| FaceRun | asset ID、检测指纹、成功/失败/零人脸、耗时、模型版本；逐图断点续跑 |
| FaceObservation | 稳定观察 ID、归一化 bbox、检测置信度、质量标记、embedding 及模型版本；不是姓名 |
| Person | 随机稳定 UUID、用户显示名、确认状态、合并别名；不按扫描次序重编 person_001 |
| PersonAssignment | face ID → person ID、机器候选/人工确认、匹配证据；人工确认不被自动覆盖 |
| Fact | 内容、主体 ID、来源照片/时间/用户确认、置信状态、适用范围、版本 |
| Event / Chapter | 成员 asset IDs、时间跨度、地点精度、参与 person IDs、使用的 fact IDs、生成版本 |
| Correction | 谁确认/合并/拆分了什么、事务 ID、旧值与新值；支持追溯和撤销 |

第一版继续用本机 SQLite 和一个顺序任务即可。现在的数据量不需要先部署图数据库；“图谱”首先是实体和有来源的关系，不要求以满屏连线作为 UI。

### 迁移时需要改进旧方案的地方

- 保留 Unicode 安全读图、归一化 embedding、检测指纹和逐图成功/失败记录。
- 不把 Haar 检测框当身份识别；没有 embedding 就不能跨图识别人。
- 不照搬连通分量的自动合并：A 像 B、B 像 C，不足以证明 A 和 C 是同一个人。尤其相似儿童，误合并会污染很多故事。
- 用多个高质量样本表示一个人，候选需通过足够相似度和与第二候选的差距；低清、侧脸、遮挡和冲突样本保留待审阅。阈值通过真实相册标注确定，旧文档的 0.45 仅是历史起点。
- 增量只检测新资产/失效指纹；已有人工确认身份锁定。模型升级显式迁移，不能以“刷新缓存”清空人物库。
- 儿童外观随时间变化，保留跨时期的多样本原型，安排少量人工复核；不承诺一次命名后几年内绝不分裂。
- 合影内多人不能轻易合并成同一个身份，同时给镜子、拼图、屏幕中的同一人物保留例外处理。
- 几千张先实测；更大规模再引入 HNSW/FAISS，避免全量 O(n²) 两两比较。
- 人脸数据、人物名称、模型权重和原片都留在账号隔离的本机数据目录，不入 Git，不发给 StepFun 做身份聚类。

引擎可用旧方案的 InsightFace + ONNX Runtime 接口，但实施时重新锁定版本和本机 provider。官方说明代码为 MIT，预训练权重另有非商业研究及授权限制，不能因代码开源就推定模型可任意商用；参赛/后续产品用途需要匹配权重授权。[InsightFace 官方许可说明](https://github.com/deepinsight/insightface#license)

本轮没有下载模型、保存 embedding 或新增人物身份断言。用户当前提出的是现状疑问与后续参考；建议下一轮先完成小样本检测和身份候选验证，再接入人物审阅。

## 4. 自动人生故事图谱的推进顺序

### 第一阶段：人和事能被可靠地合在一起

先以 20–30 张授权照片验证本人、女儿、其他儿童和多人合照。记录人脸漏检、误合并、误拆分；先解决错误合并，宁可候选分得细一些。然后用 EXIF 时间间隔、距离、AOI 和人物集合聚成事件，保留用户已有事件编辑。

输出应是“这次在公园”“几次吃甜筒”“一起做手工”的可浏览卡片，每条都有原片和依据。日期不明的照片不硬塞进生日或成长时间轴；城市级位置也不硬连精确游玩路线。

### 第二阶段：可自动发现的篇章

| 篇章 | 适用证据 | 应避免的错误 |
|---|---|---|
| 一次出游 | 相近时间、地点、环境和互动镜头 | 把不同月份假装同一天、补编先后因果 |
| 重访同地 | 同一 AOI、多个可靠日期 | 因地名一样就合并不同城市分店 |
| 相同活动 | 明确动作/物品跨日期重复 | 尚未确认身份就称为“同一个孩子越来越…” |
| 人物成长 | 已确认稳定身份、可靠日期、具体变化证据 | 仅凭照片多少或衣服不同推断成长里程碑 |
| 一起经历的日子 | 已确认关系与共同出现记录 | 将所有成年人叫家长、所有年长者叫祖父母 |

让候选排序同时考虑故事完整度、素材质量、主题差异、时间覆盖、事实可靠性和近期已生成内容。不能仅按“哪个地点照片最多”排序。

### 第三阶段：增量维护与自动成片

新增照片只影响相关人物、邻近事件和包含它们的篇章。缓存键包括资产哈希、信息卡版本、人物指派版本、事实修订和导演 skill 版本；改一句字幕不重新做人脸检测，修正一个身份只重算受影响篇章。

模型负责提议，程序负责资产存在、时间、人物确认范围、重复率和时长校验。影片保存“用了哪些事实”的依赖；发现人物认错后，可以找到并重编受影响的影片。用户修改也不能在下一轮自动生成时被覆盖。

### 参赛展示建议

做一个完整闭环：导入 → 自动信息卡 → 确认一次人物 → 地图进入真实地点 → 自动发现几个不同主题 → 自动成片 → 新增照片后补入原有故事。比增加很多未验证的图谱连线更能证明长期价值。

原始视频理解继续按 `VIDEO_MEMORY_ROADMAP.md` 作为长期计划。此轮没有扩展进视频理解、语音识别或混合原声剪辑。

## 5. 短片还应如何评价

本轮新增三个活动候选方向：雪地、甜筒、手工。镜头时长、留白、运动方式、纸面色调、转场和音乐节奏有可重复的差异。同日保留导演镜头顺序，跨日仍按可靠日期排列；最后一张的动作字幕和结语同时保留。

仍是照片短片，不是生成式运动视频。调色与音乐不同只能缓解外观雷同，真正的提升仍要靠信息质量、主体连续性、环境/互动/细节景别和恰当的取舍。

建议每次实际成片记录：

- **可信**：人物称谓、日期、地点和动作有没有编造；每句能否回指依据。
- **有故事**：看完能否说清这段回忆是什么，结尾是否自然。
- **不重复**：照片重复率、相似景别连续数、与上条片子的素材和字幕重合率。
- **有节奏**：有停顿和留白，动作与安静镜头有区别；音乐不压过照片。
- **值得保存**：用户愿不愿保留、需要改哪些句子；技术渲染成功率单独统计。

下一步最有价值的视觉功能是候选图的轻量审片：识别清晰度、主体位置、景别和近重复，再做有边界的镜头运动。当前选择保留整张照片，尚未接入人脸框，因此不主动做大幅局部裁切。
